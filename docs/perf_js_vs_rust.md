# JS vs Rust 엔진 실측 비교

`docs/native_plan.md` §0.1에 동결된 JS 베이스라인과, 같은 워크로드를 그대로 옮겨 측정한 Rust 엔진의
대조표다. **Phase 5 성능 목표(§6)의 달성 여보를 판정**하는 문서이며, 숫자는 전부 실측이다.

- 측정일: 2026-10-11 (§11의 3단 대조는 2026-10-13, HEAD `84ce01b` 기준)
- JS: `node tools/bench_baseline.mjs` · Node v24.21.0 · Phase 0.1 동결 측정값
- Rust: `cargo run -p pixel-engine --release --example bench` · rustc 1.99.0 ·
  release 프로필 `opt-level=3, lto=thin, codegen-units=1, panic=abort`
- 워크로드: **2048×1088 · 64레이어**, pen sizes [1, 8, 64], median-of-5(변형 항목은 3)

> **이 문서의 결론을 먼저(2026-10-11 갱신)**: 아래 §2의 대조표는 `PixelWriter` 장부를 고치기
> **전**에 잰 값이다. 측정 결과 쓰기 경로 전 항목이 JS보다 6~8.7배 느렸고, 원인이
> `PixelWriter::set`의 장부(BTreeMap 2회 + `dirty` 선형 탐색)로 좁혀져 §10-1에서 먼저
> 고쳤다. **고친 뒤 다시 잰 값이 §2-1이다.** 거기서는 13항목 중 11항목이 JS를 앞서고,
> `stroke pen=1`은 2.8배 느림 → 4.2배 빠름으로 뒤집혔다.
>
> 즉 이 문서의 최종 요지는 두 단계로 읽어야 한다:
> ① **"Rust가 느리다"는 진단은 데이터 구조 선택의 문제였다**(§2·§4-1).
> ② **고치니 언어 우위가 드러났다**(§2-1). 남은 미달은 이제 진짜 알고리즘 문제다(§2-2).
>
> **2026-10-13 추가**: §11이 그 2단계 이후를 다룬다 — 커버리지 비트마스크·스팬 쓰기·
> 루프 인터체인지·rayon·`floor` 제거·**BTreeMap → dense 배열 인덱스**를 전부 적용한 뒤의
> 3단 대조(JS / Rust 이전 / Rust 이후). **목표 9항목 중 6항목 달성(0 → 6)**.
> §2·§2-1·§2-2는 그대로 두고 읽으면 된다.

## 1. 측정 조건

두 숫자가 **비교 가능**하려면 같은 입력· 같은 샘플 규칙· 같은 기계가 필요하다. 그래서 JS 쪽을
고치지 않고 Rust 쪽을 JS에 맞췄다.

| 항목 | JS 베이스라인 | Rust 벤치 |
|---|---|---|
| 실행 | `node tools/bench_baseline.mjs` | `cargo run -p pixel-engine --release --example bench` |
| 런타임 | Node v24.21.0(V8) | rustc 1.99.0, `opt-level=3`, `lto=thin`, `codegen-units=1` |
| 캔버스 | 2048×1088 | 2048×1088 |
| 레이어 | 64 | 64 |
| pen | 1 / 8 / 64 | 1 / 8 / 64 |
| 샘플 | median-of-5, 변형 항목(floodFill·exportPng)은 3 | 동일 |
| 워밍업 | JS는 없음(V8 JIT 워밍) | 명시적 1회 |

### 동일하게 맞춘 것들

- **busy document 구성이 같다**: 모든 레이어가 내용을 갖고, `opacity=0.5`는 4번째마다,
  blend 모드는 6종을 순환, `stroke_segment` pen=5 대각선 24회를 두 색으로 교차시킨다.
- **`strokeSegment` 좌표 생성식이 같다**: `(k*97) % W`, `(k*61) % H` 류의 식을 그대로 옮겨
  같은 픽셀 분포가 나오게 했다. 경로가 조금만 달라져도 BTreeMap 페이지 접근 패턴이 바뀌어
  비교가 무의미해진다.
- **`floodFill`은 샘플마다 새 저장소를 쓴다.** walk가 입력을 변형하므로, 이미 채워진 캔버스를
  재시간 측정하면 early-out만 잰다. JS 파일의 주석에 적힌 이유를 그대로 보존했다.
- **`exportPngBytes` 안에 flatten을 포함**한다. JS는 `exportPngBytes`가 내부적으로
  `flattenToRgba`를 부르므로, Rust도 같은 경로를 재현했다.
- `flattenToRgba`의 per-pixel 루프·직접 대체 단축·`over_blend` 호출·알파 0시 RGB 클리어 규칙은
  이번에 포팅한 `io/export.rs`가 JS와 동일하게 갖는다. 단, JS의 16진 배경색 경로는
  문서 모델(Phase 1.12)이 없어 범위 밖 — 코드 주석에 명시했다.

### 한쪽에만 있는 것

JS 14항목 중 두 항목은 Rust에 대응물이 없다.

| 항목 | 상태 |
|---|---|
| `documentToJson (save)` | **미측정** — Phase 1.13 `io/serialize` 포팅 분에서 측정 |
| 저장 JSON 크기 7557 KB | **미측정** — 같은 이유 |

**측정하지 않은 것은 통과한 것이 아니다.** 이 문서에서 빠진 숫자를 달성으로 읽으면 안 된다.

composite·flatten·exportPng는 변하지 않을 것으로 예상되지만, **예상은 측정이 아니다** —
재측정 전까지 수정 전 값을 유효한 값으로 취급한다.)

**무엇이 달라졌나**: 수정은 코드 한 곳이다. `dirty`가 `Vec<(u32,u32)>`에서
`BTreeSet<u64>`(청크 키)로 바뀌었고, `take_dirty`는 이제 키 오름차순을 그대로 쓰므로
정렬이 사라졌다. `chunk_key = cy*64+cx`이므로 **키 순서가 곧 (cy,cx) 순서**다.
여기에 직전 청크를 기억하는 `last_key` 메모를 둬서, footprint가 한 청크에 쓰는
~3,000 픽셀이 장부를 한 번만 건드리게 했다.

**빠른 이유는 할당 제거가 아니라 되풀이 제거다.** 수정 전 `touch()`는 픽셀마다
①`before.entry()` BTreeMap 프로브 ②`dirty.contains()` 선형 탐색 을 했다. ②가 픽셀 수가
아니라 **지금까지 만난 청크 수**에 비례하므로, pen=64가 수천 청크를 만지면 전체가
제곱으로 갔다. 이제 픽셀 하나의 장부 비용은 정수 비교 한 번이다.

> 이 수정이 Saga인 이유: §4-1의 분해 표에서 `PixelWriter::set`이 271.9 ns/write,
> `ChunkStore::set_pixel`이 10.8 ns/write였다. 장부가 25배였으므로, 장부만 없애도
> 이론상 185 ns → 12 ns/write, 즉 15배. 실제로 pen=8은 387→28 ms로 **13.6배** 빨라졌다.

### 2-2. 수정 후에도 남은 미달 — 이제는 진짜 알고리즘 문제

수정 후 배수로 보면 미달은 두 종류로 갈린다.

- **거의 도달(1.1~2.6배)**: pen=1·floodFill ×2·ellipse·polygon. 쓰기 한 건이
  `ChunkStore::set_pixel`(10.8 ns)으로 수렴했으므로, 이 구간은 이제 **쓰기 횟수 자체**를
  줄여야 한다. 예컨대 pen=64의 footprint는 한 행이 **연속된 구간**인데(원판 부등식이
  행별로 단조), 지금은 셀 3,228개를 하나하나 찍는다. 행 단위 span 쓰기로 바꾸면
  쓰기 횟수가 64분의 1로 줄어 pen=64는 즉시 목표 이내에 들어온다.
- **구조적으로 먼 거리(5~69배)**: stroke pen=8·64, ellipse. 쓰기 수가 절대적으로 커서
  위의 span 최적화가 전제 조건이다. composite·flatten·exportPng은 쓰기와 무관하므로
  §4-5·§4-6의 원인이 그대로 남는다(청크 해석 호이스트·SIMD·rayon).

### 순위 요약

배수는 아래에서 **JS ÷ Rust**로 쓴다(1보다 크면 Rust가 빠른 것).

- **Rust가 빠른 항목(5)**: composite 2.50× · strokePoint 1.94× · rrect 1.20× ·
  flatten 1.09× · exportPng 1.13× — 모두 **쓰기량이 적거나, 청크 해석을 픽셀 루프 밖으로
  뺀 경로**다.
- **Rust가 거의 비슷하거나 약간 느린 항목(1)**: line 1.58×
- **Rust가 2.8~8.7배 느린 항목(7)**: stroke pen=1 · pen=8 · pen=64 · floodFill ×2 ·
  ellipse · polygon — 공통점은 **픽셀 하나당 `PixelWriter` 장부 갱신**이 전부라는 점이다(§4-1).

## 4. 항목별 원인 — 실제로 무엇이 시간을 쓰는가

### 4-1. 쓰기 경로 공통: `PixelWriter::set`의 장부가 전부를 지배한다

`stroke`·`floodFill`·`applyShape` 셋 다 **쓰기 한 건의 비용**으로 거의 설명된다. 샘플당 실제
쓴 픽셀 수를 세어(카운터 싱크로 측정) 나눠보면:

| 항목 | 샘플당 쓰기 수 | JS ns/write | Rust ns/write |
|---|---:|---:|---:|
| stroke pen=1 | 40,580 | 66.4 | 183.8 |
| stroke pen=8 | 2,110,160 | 21.3 | 183.5 |
| stroke pen=64 | 130,992,240 | 21.3 | 185.5 |
| floodFill 빈 캔버스 | 2,228,224 | 65.6 | 512.7 |
| ellipse fill | 823,592 | 24.8 | 201.5 |
| polygon fill | 781,577 | 34.3 | 201.6 |

**Rust는 항목과 무관하게 185~200 ns/write로 수렴한다.** 이것은 우연이 아니다.
`PixelWriter::set`이 매 픽셀마다 두 개의 장부를 갱신하기 때문이다.

1. `touch(x, y)` — 청크 키를 만들고 `before` BTreeMap에 엔트리를 만든다(클론 아님, 첫 방문만).
   `if !self.dirty.contains(&(cx, cy))`는 **`Vec`을 선형 탐색**한다. 청크가 늘어날수록
   이 선형 탐색이 길어진다 — busy document는 레이어당 586개 청크를 갖는다.
2. `store.set_pixel` — 또 한 번 BTreeMap 조회 후 4바이트 기록.

`BTreeMap`은 Rust 표준 컬렉너 중 JS `Map`과 가장 가까운 선택이지만, **해시가 아니다.**
키가 `u64` 정수인데도 삽입/조회마다 트리를 탄다. JS의 `Map`은 V8이 해시 테이블로 구현하고
키가 정수면 해시가 거의 항등에 가까워져, 조회가 상수 시간에 끝난다. 같은 희소 저장 구조를
선택했는데 구현체 특성이 10배 차이를 만든 것이다.

실측으로 확인한 분해(별도 프로브, [별첨](#8-별첨--보조-측정) 참고):

| 구성 | 2.2M writes |
|---|---:|
| `ChunkStore::set_pixel` 직접(BTreeMap 1회) | 24.0 ms |
| `PixelWriter::set`(장부 + BTreeMap 2회) | 605.7 ms |

즉 **장부가 저장 자체의 25배**다. 이것이 쓰기 경로 전 항목의 지배 원인이다.

### 4-2. stroke pen=1은 작고 pen=64는 큰 이유

둘 다 같은 코드를 탄다. 차이는 **펜 하나가 찍는 픽셀 수**뿐인데, 양쪽의 비용 구조가 달라
배수가 벌어진다.

| pen | footprint 셀 수 | 샘플당 write | JS ns/write | Rust ns/write | 배수 |
|---:|---:|---:|---:|---:|---:|
| 1 | 1 / 1 (100%) | 40,580 | 66.4 | 183.8 | 2.77× 느림 |
| 8 | 52 / 64 (81%) | 2,110,160 | 21.3 | 183.5 | 8.63× 느림 |
| 64 | 3,228 / 4,096 (79%) | 130,992,240 | 21.3 | 185.5 | 8.72× 느림 |

- **pen=1이 가장 양호한 이유.** write 수가 4만 개로 적어, Bresenham walk 자체의 고정비가
  상대적으로 큰 비중을 차지한다. 그래도 장부가 지배해 2.77배 느리다.
- **pen=8·64은 거의 같은 배수(8.6·8.7배)다.** write 수가 52배·3,228배로 늘어 고정비가 완전히
  희석되고, **장부가 거의 전부**가 된다. Rust의 `ns/write`가 183.5·185.5로 같은 것도 그 증거.
- footprint가 n²의 80% 안팎으로 모든 크기에서 비슷하므로, **배수를 가르는 변수는 footprint
  비율이 아니라 절대 픽셀 수**다.

JS 쪽은 정반대다. `stampBrush`가 footprint 전체를 훑어 `mask[by*n+bx] === 1`인 셀만
`writer.set`을 부르므로, 안 찍는 셀은 비용이 0이다. 그래서 JS의 `ns/write`가 21 ns로
**펜 크기와 무관하게 일정**하게 수렴한다(pen=1의 66 ns는 아래 메모 참고).

한 가지 메모: pen=1의 JS 66.4 ns/write는 pen=8/64의 21.3 ns보다 3배 높다. 이건 배경이
빈 레이어라 `before` 엔트리를 처음 만드는 분기가 매 샘플 반복되고, Bresenham 스텝당
footprint가 1개라 호출 수가 적어 JIT 워밍이 덜 됐기 때문으로 보인다.
2026-10-11 재실행에서 1.503 ms가 나와 **동결값 2.69 ms와 44% 차이**가 났다(§7-3 참고).

### 4-3. floodFill: JS는 같은 알고리즘인데 왜 7~8배 느린가

`flood_fill_scanline`은 1:1 포팅이라 알고리즘은 같다. 차이는 **채우는 방법**이다.

JS `fill.js`는 싱크에 콜백을 넘겨 `(x, y, p) => writer.set(x, y, p)`를 부른다. Rust도
`PixelSink` 트레이트로 같은 구조지만, **구현체가 `PixelWriter`**이므로 §§4-1의 장부 비용을
그대로 물린다. 게다가 span 스캔은 `sink.get(x, y)`도 수만~수백만 번 부르는데, 이것도
`PixelWriter::get` → `ChunkStore::get_pixel` → **BTreeMap 조회**다.

| 단계 | 쓰기 수 | JS ms | JS ns/write | Rust ms | Rust ns/write |
|---|---:|---:|---:|---:|---:|
| 빈 캔버스 채우기 | 2,228,224 | 146.2 | 65.6 | 1142.8 | **512.7** |
| 이미 RED → 초록 | 2,228,224 | 165.2 | 74.2 | 1142.9 | **512.7** |

Rust의 `ns/write`가 stroke의 185보다 **2.8배 높은 513**인데, 이 차이는 쓰기만으로는
설명되지 않는다. 스캔라인 walk는 span 경계를 찾기 위해 `sink.get`을 왼쪽·오른쪽으로 반복
호출하는데, `PixelWriter::get` → `ChunkStore::get_pixel` → **BTreeMap 조회**가 그대로
물린다. 즉 쓰기당 조회가 1회가 아니라 수 회 발생한다. 이것이 쓰기 513 ns/건의 주된 원인으로
보이는데, 엄밀히 말해 **읽기와 쓰기의 분담은 이 측정만으로는 분리되지 않는다**(둘을 따로
세는 프로브는 돌리지 않았다). 다만 "빈 캔버스"와 "이미 RED"의 시간이 0.14% 차이로 같은 것은
walk 형태가 동일하고 읽이든 쓰이든 같은 BTreeMap을 탐한다는 뜻이다.

Phase 5.4(행 밴드 분할)는 이 항목을 겨냥하지만, **분할해도 BTreeMap 조회는 남는다**.
5.4 전에 `PixelWriter` 장부와 `ChunkStore` 조회를 먼저 고쳐야 5.4의 이득이 보인다(§5).

### 4-4. applyShape: 마스크는 빠른데 찍는 게 느리다

네 항목 모두 **쓰기 한 건의 비용**으로 설명된다(§4-1). 표의 `ns/write`는 항목 시간을
실제 쓴 픽셀 수로 나눈 것이다.

| 항목 | 쓰기 수 | JS ms | JS ns/write | Rust ms | Rust ns/write |
|---|---:|---:|---:|---:|---:|
| ellipse 1024² fill | 823,592 | 20.4 | 24.8 | 165.9 | **201.4** |
| rrect 외곽 sw=4 | 15,924 | 11.1 | 696.9 | 9.3 | **582.6** |
| line sw=8 | 18,653 | 4.22 | 226.2 | 6.7 | **356.7** |
| polygon 32-gon fill | 781,577 | 26.8 | 34.3 | 157.6 | **201.6** |

- **ellipse·polygon은 8.1배·5.9배 느리다.** 82만/78만 건의 장부 갱신이 전부이며,
  `ns/write`가 201로 수렴한다. 별첨에서 마스크만(sink 없이) 5회 = 4.95 ms이므로, 마스크
  자체는 항목 시간의 **0.6%**에 불과하다. **99% 이상이 장부다.**
- **rrect은 Rust가 이긴다**(1.20배). 쓰기가 1.6만 개뿐이라 장부가 작고, 나머지는 JS가
  `outlineRing`을 매번 다시 계산하는 비용이 크다. Phase 5 없이도 이기는 대표 예다.
- **rrect·line의 `ns/write`(583·357)가 ellipse·polygon(201)보다 높은 이유는 쓰기가 느려서가
  아니다.** 쓰기 수가 1/50 수준이어서 항목 시간의 대부분이 **마스크 생성**에 가므로,
  시간을 쓰기 수로 나누면 마스크 비용까지 쓰기 한 건에 얹혜 나온다. 이 두 행은 마스크 대
  쓰기의 구성비를 보여 주는 참고값이지, 쓰기 단위 비용 비교는 아니다.
- **ellipse·polygon이 쓰기 단위 비용의 기준**이다. 82만/78만 건에서 마스크가 0.6%로
  희석되므로 201 ns/write가 거의 순수 장부 비용이고, 이 수치가 §4-1의 분해값과 같은 급이다.
- 따라서 **"마스크 → 쓰기" 경계에서 Rust는 이기고, 쓰기로 넘어가는 순간 진다.**
  장부만 고치면 ellipse·polygon은 즉시 목표(≤1 ms, ≤2 ms)에 근접한다.

### 4-5. flattenToRgba 1.09배 — 이겼는데 목표는 670배

가장 설득력이 필요한 숫자다. 목표는 ≤3 ms인데 실측 1844 ms로, **목표의 615배**다.
동시에 JS를 1.09배 앞선다. 왜 이렇게 애매한가.

**1) per-pixel BTreeMap 조회가 지배한다.** 새로 포팅한 `io/export.rs`는 JS와 같은
per-pixel 루프를 쓰고, 각 픽셀마다 64개 레이어를 돌며 `store.get_pixel(x, y)`를 부른다.
ChunkStore의 `get_pixel`은 **대상 청크를 찾는 BTreeMap 조회**다. 한 번 flatten에
2,228,224 × 64 = 1.4억 회의 BTreeMap 조회가 일어난다.

| 구성 | 시간 |
|---|---:|
| flattenToRgba (Rust) | 1844.0 ms |
| flattenToRgba (JS) | 2002.3 ms |
| 차이 | 158.3 ms (**1.09배**) |

**2) JS의 배열 할당이 생각보다 적다.** §0.1의 읽을거리는 "flatten이 composite의 5배"라고
했는데, 실제로 flatten은 `over_blend` 경로에서만 배열 2개를 만든다. busy document에서
직접 대체 단축 자격이 있는 레이어는 **5개**(li = 6·18·30·42·54)뿐이고, 나머지 59개는
`over_blend`를 탄다. 그런데 비가연(non-transparent) 레이어-픽셀은 전체의 **4.5%**(648만 건)에
불과하므로, `over_blend`는 픽셀당 64회가 아니라 **약 598만 회** 호출된다. JS가 배열을
만드는 횟수는 2×598만 = 1,196만 개 수준이다. 절대적으론 많지만, flatten 전체를 지배하지는
않는다. 주범은 **1.426억 회의 `getPixel` 조회**다.

비교: 1.4억 회 조회에 1844 ms면 **13.1 ns/조회**. BTreeMap 1회 조회가 13 ns라는 뜻이고,
이건 트리 깊이 + 포인터 추적으로 나온 값이다. **최적화가 아니라 할당 제거가 아니라,
조회 비용이 거의 그대로 남은 것**이다.

### 4-6. composite 2.50배 — 단축이 아니라 호이스트와 할당 제거

composite Phase 5 목표(≤2 ms)를 향해 움직인 유일한 항목이다. 이유는 세 가지가 겹친다.

**1) 픽셀 대부분이 알파 0이라 내부 루프가 비교 한 번으로 끝난다.** 레이어-픽셀 슬롯
1.426억 개(2176 청크 × 1024 픽셀 × 64 레이어) 중 비가연은 **4.5%**(648만 건)뿐이다.
나머지 95.5%는 `sa8 == 0 → continue`, 즉 바이트 하나 비교하고 넘어간다. 이 비용은
JS(`data[o+3]`)와 Rust(`data[o+3]`)가 거의 같다.

**2) 청크 해석을 픽셀 루프 밖으로 뺀 것은 양쪽이 같다.** `visible_sources`(JS의
`visibleSources`)가 청크당 레이어 한 번만 훑으므로, BTreeMap 조회는 2176×64 = **13.9만 회**
에서 끝난다. flatten이 같은 일을 **1.426억 회** 하는 것과 대비된다(§4-5). 이것이 composite가
빠른 결정적 이유고, JS도 이미 이 구조를 갖고 있었다.

**3) 그래서 이긴 쪽은 할당과 루프 조밀도다.** busy document에서 직접 대체 단축 자격이 있는
레이어는 5개뿐이다(normal 모드 11개 중 opacity 1인 `li` = 6·18·30·42·54). 나머지 59개는
`over_blend`를 타고, 그 호출은 약 **598만 회**. JS는 호출마다 배열 2개를 새로 만들고,
청크당으로도 `srcs` 객체 배열을 만든다(2176×64). Rust는 레지스터 안의 `[u8;4]`로 끝난다.
**즉 composite의 2.5배는 단축 덕분이 아니라 — 이 워크로드에서는 단축이 거의 작동하지
않는다 — 알파 0 생략 + 청크 해석 호이스트 + 할당 제거의 합이다.**

> 그런데도 목표(≤2 ms)에는 **78배 못 미친다**. `visible_sources`가 청크당 BTreeMap 조회
> 64회를 한다는 점은 작지만, 그 뒤의 1024픽셀 × 64레이어 = 6.6천만 회의 `data[o]`
> 인덱싱이 대부분이고, 이 루프를 SIMD(5.1)나 rayon(5.2)으로 쪼개는 게 목표에 도달하는
> 유일한 길이다.

### 4-7. exportPngBytes 1.13배 — deflate는 이미 끝났다

`export_png`는 `flate2`(miniz_oxide) + 직접 구현 CRC32·필터0 인코드이다. 별첨에서
8.9 MB RGBA → 36 KB IDAT가 **15 ms**에 끝난다. deflate가 15 ms인데 항목이 1833 ms라는 건
**flatten이 1818 ms를 먹었다**는 뜻이다. 따라서 이 항목은 flatten과 같은 운명이다.

Phase 5.5(PNG 인코드 병렬 + 레벨)는 **이미 만족 상태** — 40 ms 목표는 flatten만 고치면
자동으로 달성된다.

Phase 5의 기법(5.1~5.4)은 이 구조가 정리된 뒤에 켜야 배수가 보인다.

## 7. 방법론 주의점

1. **JS와 Rust는 다른 평가기다.** 같은 기계에서 돌았지만, V8 JIT(인터프리터 → 스파크플러그 →
   터보팬 단계를 거쳐 실행 중 최적화)와 AOT 정적 컴파일(+LTO)은 같은 코드에서 다른 절대값을
   낸다. 이 비교는 "Rust가 JS보다 빠르다"는 주장이 아니라, **JS 베이스라인 대비 Rust 엔진의
   현재 진전**을 보여주는 데 의미가 있다.
2. **median 단일 실행이다.** 데스크톱 기기에서 한 번씩만 돌렸다(각 5회 샘플의 median).
   §1 벤치를 두 번째로 실행한 값을 함께 적어 재현성을 보조 근거로 삼는다:

   | 작업 | 실행1 median | 실행2 median | 차이 |
   |---|---|---:|---:|
   | stroke pen=1 | 7.463 | 7.418 | −0.6% |
   | stroke pen=8 | 387.476 | 388.983 | +0.4% |
   | stroke pen=64 | 24296.477 | 24365.296 | +0.3% |
   | strokePoint pen=64 | 0.050 | 0.055 | +10% |
   | floodFill 빈 캔버스 | 1142.762 | 1154.143 | +1.0% |
   | floodFill 빨강→초록 | 1142.901 | 1151.328 | +0.7% |
   | ellipse fill | 165.866 | 174.376 | +5.1% |
   | rrect 외곽 | 9.278 | 9.439 | +1.7% |
   | line sw=8 | 6.652 | 6.648 | −0.1% |
   | polygon fill | 157.580 | 158.508 | +0.6% |
   | composite | 156.251 | 162.638 | +4.1% |
   | flattenToRgba | 1843.971 | 1893.497 | +2.7% |
   | exportPngBytes | 1833.090 | 1890.501 | +3.1% |

   편차가 5%를 넘는 항목은 strokePoint(절대값 0.05 ms라 의미 적음)·ellipse·composite뿐이다.
   **큰 항목의 순위는 재현된다.**
3. **동결 베이스라인과 오늘 재측정값은 다르다.** JS 베이스라인을 다시 돌려봤다:

   | 작업 | 동결(Phase 0.1) | 2026-10-11 재실행 | 차이 |
   |---|---|---:|---:|
   | stroke pen=1 | 2.69 ms | 1.503 ms | **−44%** |
   | stroke pen=8 | 44.9 ms | 45.223 ms | +0.7% |
   | stroke pen=64 | 2785.7 ms | 2933.784 ms | +5.3% |
   | floodFill 빈 캔버스 | 146.2 ms | 172.401 ms | +18% |
   | ellipse fill | 20.4 ms | 21.601 ms | +5.9% |
   | composite | 391.2 ms | 386.997 ms | −1.1% |
   | flattenToRgba | 2002.3 ms | 2056.175 ms | +2.7% |
   | exportPngBytes | 2070.7 ms | 2147.555 ms | +3.7% |
   | documentToJson | 1909.7 ms | 2060.824 ms | +7.9% |

   pen=1만 44% 벌어졌다(§4-2). 재실행으로 바꾸면 pen=1의 Rust 배수는 2.77× → 3.69×로
   **더 나빠 보인다**. 본문 표는 동결값을 썼으므로, 이 항목만큼은 동결값을 쓰지 않은
   재실행값이 오히려 Rust에게 관대했을 수 있음을 알아둘 것. 그 외 항목은 20% 이내.
   **floodFill 빈 캔버스는 반대 방향이다.** 동결값 146.2 ms를 쓰면 7.82배 느린데, 재실행값
   172.4 ms를 쓰면 6.7배로 완화된다. 즉 본문의 그 숫자는 Rust에게 **불리한 쪽**을 고른
   값이다. 양쪽 다 같은 순서를 가리키므로 결론은 흔들리지 않는다.
4. **floodFill 두 항목은 신선한 상태가 필요하다.** walk가 입력을 변형하므로 샘플마다
   저장소를 새로 만든다. JS도 같은 `timeFresh`를 쓰며, 이 규칙을 어기면 이미 채워진 캔버스의
   early-out만 측정한다.
5. **JS `flattenToRgba`는 픽셀당 배열 2개를 할당한다** — 단 `over_blend` 경로에서만,
   비가연 레이어-픽셀의 4.5%에서만 발생한다. §0.1의 진단은 방향은 맞으나 **비중은 과대평가**됐다.
   실측 원인은 `getPixel`의 1.426억 회 조회다(Rust는 BTreeMap, JS는 해시 `Map`).
6. **busy document의 구성은 의도된 최악값이다.** 모든 레이어가 내용을 갖고 블렌드가 6종
   순환하므로, 직접 대체 단축은 오히려 **거의 작동하지 않는다**(§4-6). 실제 도구 사용 —
   단일 레이어에 normal 모드 펜칠 — 에서는 단축이 활성화되어 composite가 훨씬 빠르다.
   따라서 이 표의 composite 숫자는 **특정 사용 패턴을 대표하지 않는다**.
7. **Rust 벤치는 `std::time::Instant`**를 쓰고, JS는 `performance.now()`를 쓴다.
   둘 다 OS 제공 단조 시계이므로 공변이다.

| **레이어 단위 워드 스킵** | `composite.rs`, `io/export.rs` | 64픽셀 워드 안에서 **그 레이어의 마스크 워드가 0이면 그 레이어를 통째로 건너뛴다** | composite 1.18× (위 두 개와 합쳐 1.68×) |
| **`floor` 제거** (벡터연산/SIMD) | `blend.rs` | `rnd(v) as u8` → `(v + 0.5) as u8`. `f64::floor`는 `roundsd`(SSE4.1)를 요구하는데 x86-64 베이스라인은 SSE2라 비트마스크 시퀀스로 풀린다. Rust의 `as` 캐스팅은 0 방향 절삭 + 포화이므로 **모든 f64에서 바이트가 같다** | composite 1.21×, exportPng 1.13× |
| **스탬프 중복 제거** | `raster/brush.rs` (`stroke_segment`) | 한 번의 호출이 이미 칠한 행 구간을 기억해 겹치는 부분을 건너뛴다. pen=64는 1스텝당 3,228픽셀을 **1픽셀 전진**에 쓴다 | **pen=64 4.1×**, pen=8 1.13× |
| **dense 배열 인덱스** (자료구조) | `chunkstore/store.rs` | `BTreeMap<u64, ChunkCell>` → `Vec<Option<ChunkCell>>`. `chunk_key = cy*64+cx`가 **그 자체로 배열 인덱스**라서 탐색 자체가 사라진다 | stroke 계열 **1.6~2.9×**, floodFill 1.5×, flatten 1.11× |
| **rayon** | `flatten_to_rgba`, `composite_canvas` | 청크 행은 서로 독립. 1스레드 쌍을 **같이 남겼다** | composite 7.0×, flatten 7.1× |

### 11-2-1. dense 배열 인덱스 — 남은 BTreeMap 제거

청크 인덱스가 **마지막으로 남아 있던 약점**이었다. §11-2의 다른 기법들은 읽기
경로의 프로브를 청크당 1회로 줄였지만, 쓰기/스캔 경로는 **여전히 32픽셀마다 한 번씩**
저장소를 찔렀다.

| 경로 | 프로브 빈도 (busy document) |
|---|---|
| flatten / composite | 청크당 1회 → 14만 회 (전체의 ~2%) |
| **stroke pen=64** | `set_run`이 32픽셀 조각마다 1회 → **약 500만 회** |
| **floodFill** | 행 스캔이 32픽셀당 1회 → **약 20만 회** |
| ellipse / polygon | 런당 1~2회 → 약 3만 회 |

`BTreeMap`에서는 이 500만 번이 전부 **4~5단 의존 로드**(대부분 캐시 미스)였다.
dense 인덱스로 바꾸면 **경계 검사 한 번 + L1/L2에 남은 테이블에서 로드 한 번**이다.

| 항목 | BTreeMap | dense 배열 | 개선 |
|---|---:|---:|---:|
| stroke pen=1 | 0.599 ms | **0.221 ms** | **2.7×** |
| stroke pen=8 | 7.548 ms | **4.124 ms** | 1.83× |
| stroke pen=64 | 48.118 ms | **29.260 ms** | 1.64× |
| floodFill 빈 캔버스 | 9.784 ms | **6.091 ms** | 1.61× |
| polygon fill | 1.189 ms | **0.921 ms** | 1.29× |
| flatten 1스레드 | 113.995 ms | **103.586 ms** | 1.10× |

**읽기 경로는 거의 안 변한다(1.03~1.11배) — 예상대로다.** 청크당 1회 프로브였으므로
제거할 것이 없었다. 이득은 전부 "32픽셀마다 찌르던" 경로에서 나왔다.

#### 무엇을 포기했나

- **메모리**: 존재 여부와 무관하게 슬롯 하나당 8바이트. 최대 캔버스에서
  `64 * 34 * 8` = **17 KB/레이어**, 64레이어 최악값이면 1.1 MB(청크 데이터 570 MB 대비).
  "거의 빈 레이어는 거의 안 든다"는 성질이 **거의(17 KB)**에서 **없음**으로 바뀐다.
- **배열 stride는 `chunks_x`가 아니라 `MAX_CHUNKS_X`(64)**다. `chunk_key`가 그 stride로
  정의되어 있고, **stride를 같게 유지해야 resize가 청크를 옮기지 않는다.** 폭만 바뀌면
  어떤 청크도 이동하지 않고, 높이만 바뀌면 배열 길이만 바뀐다. (처음에 `chunks_x` stride로
  짜서 `len is 4 but the index is 64`로 전부 깨졌다.)
- **진짜 존재 비트맵(청크당 1비트)은 넣지 않았다.** `Option<Box<..>>`가 이미
  nul niche로 8바이트라 "빈 슬롯 판정"이 로드 한 번이고, 더 줄이려면 슬롯을
  `u32` 오프셋으로 좁혀야 하는데 그러면 청크 데이터에 대한 간접이 두 겹이 된다.
  **저장/직렬화처럼 "전부 순회"하는 경로가 병목이 될 때** 그때 고려할 값이다.
- `Debug`를 손으로 썼다. dense 테이블에 `#[derive(Debug)]`를 걸면 4096바이트 청크가
  수천 개씩 출력된다.

### 11-3. 알고리즘과 병렬을 분리하면

`composite`와 `flatten`에 rayon을 켰으므로, "알고리즘이 이만큼"과 "병렬이 이만큼"을
갈라 적어야 한다. 둘 다 **같은 함수를 1스레드로 부르는 쌍**을 붙여 뒀다.

| 작업 | 이전 | 이후 1스레드 | 이후 rayon | 알고리즘+자료구조 | 병렬 |
|---|---:|---:|---:|---:|---:|
| composite 2176×64 | 171.369 ms | 103.040 ms | **14.266 ms** | 1.66× | 7.2× |
| flatten 2048×1088 | 2227.665 ms | 103.586 ms | **14.697 ms** | 21.5× | 7.0× |

**flatten은 알고리즘과 자료구조가 21.5배를 냈다** — §10-3(청크 해석 호이스트)이 그 전부다.
composite는 1.66배, 병렬 7.2배다. composite가 비싼 이유는 §4-6이 이미 말했다: 이
워크로드에서 픽셀의 95.5%가 알파 0이라 **실제 블렌드 연산이 648만 회**뿐인데, 그것을
둘러싸고 있던 6.6천만 회의 인덱싱이 원래 비용의 대부분이었다 — 그 인덱싱을 줄인 뒤
남은 건 `over_blend`의 f64 연산 그 자체다.

### 11-4. 왜 비트마스크가 composite에서 덜 먹었나 — 그리고 그래도 남긴 이유

§4-6의 직관과 다른 게 하나 있다. **비트마스크가 composite에는 flatten만큼 이득이
없었다.** 이유는 합집합이다.

> 각 레이어는 2176청크 중 586개(26.9%)에만 내용을 갖고, 그 안에서도 픽셀의
> ~4.5%만 알파가 0이 아니다. 64레이어의 커버리지를 OR 하면 **거의 모든 워드가 켜진다.**
> 즉 청크 단위 합집합은 이 워크로드에서 밀도를 걸러내지 못한다.

그래서 두 겹으로 나눴고, 둘 다 필요하다:

- **청크 단위 합집합** (`coverage_union`) — 얕은 스택(2~3레이어)에서 이득이 크다.
  이 워크로드에서는 거의 빈 일. 그래도 16 워드 OR는 1024회의 바이트 로드보다 싸므로
  남겼다.
- **레이어 단위 워드 스킵** (`if s.mask[w] == 0 { continue }`) — **이쪽이 composite의
  진짜 수단이다.** 64레이어 각각이 자기 워드에서 84% 비어 있다.

### 11-5. 아직 측정하지 않은 것 — 통과한 것이 아니다

| 항목 | 상태 |
|---|---|
| `documentToJson (저장)` | **미측정.** `io/serialize::document_to_json`은 phase 1.13에서 생겼지만 `&Document`를 받고 `serde_json::Value`를 반환한다. JS 쪽은 `documentToJson` + `JSON.stringify`(7.5 MB 문자열)를 잰다. **문자열 직렬화 경로가 없어 숫자를 붙여도 비교가 아니다.** |
| 저장 JSON 크기 (JS 7557 KB) | 같은 이유로 미측정 |
| Undo/히스토리 바이트 예산 | 커버리지 비트마스크가 청크당 128바이트를 더한다(문서 전체 +3.1%). `UNDO_MAX_BYTES`(96 MB) 예산에 대한 회귀 측정은 **하지 않았다** |
| 빈 레이어의 메모리 | dense 슬롯 테이블이 레이어당 최대 17 KB(§11-2-1). 실측하지 않았다 |
| 프레임 시간·UI 반응성 | 미측정. `composite_canvas`/`flatten_to_rgba`에 rayon을 넣었지만, 화면 갱신 경로는 여전히 `comp_cache/paint.rs`의 단일 스레드 `composite_chunk`다. **6 ms 프레임 예산 경로에는 rayon이 들어가지 않았다** |
| 레이어 수 1~3에서의 composite | 미측정. §11-4 때문에 이 구간에서 비트마스크가 가장 크게 먹을 것으로 보이지만 **숫자로는 없다** |

### 11-6. 이 작업이 부수적으로 고친 것 (성능 밖)

- `ChunkStore`의 청크 엔트리에 커버리지 비트마스크가 딸려 있다. `get_chunk_with_mask`가
  둘을 한 번에 준다. 쓰기 3곳 외의 경로로 청크에 손대는 곳이 생기면
  `refresh_chunk_mask`를 부르거나, 그 경로를 테스트가 덮어야 한다
  (`the_alpha_mask_never_drifts_from_the_bytes`가 그 보험).
- `PixelWriter::set_run`이 **오프캔버스에서 시작하는 런을 잘라낸다(버리지 않는다)**.
  첫 버전은 음수 x를 만나면 런 전체를 버렸고, 그 결과 합성 테스트 여섯 개가 깨졌다.
  `set`이 픽셀별로 클립하므로 런도 그렇게 해야 한다.
- `mark_range`의 워드 경계는 **열이 아니라 비트 오프셋에서** 계산해야 한다. 행이 32픽셀
 이라 한 행은 워드 두 개를 못 넘지만, 2행을 1워드에 묶으므로 행 1의 열들은 워드 0의
  *위쪽* 절반이다. 고정된 열 경계를 쓰면 이웃 행으로 새었다.

### 11-7. 다음에 할 일 (남은 미달 3항목, 순서대로)

1. **`over_blend`의 f64 연산 자체.** composite 직렬 103 ms 중 대부분이 648만 회의
   블렌드다. 자료구조·hoist·스킵을 다 걷어냈으니 **이것만 남았다.** 정수 근사로 바꾸면
   빠르지만 바이트가 달라지고, 비트 동일성을 지키면서 줄이는 유일한 길은 "이 워크로드가
   실제로 만드는 `(da, sa, mode)` 조합에 대한 완전 탐색표"인데 — 그 표가 **정말**
   빠르려면 어떤 조합이 나오는지 먼저 데이터로 알아야 한다. 지금은 손대지 않았다.
2. **ellipse 1.621 ms (목표 1 ms).** §8-2의 분해대로 마스크 생성이 ~1 ms다. 쓰기는 이미
   스팬이라 줄일 곳이 아니다. 마스크를 행별 비트셋으로 만들고 `trailing_zeros`로 런을
   뽑으면 될 것으로 보이지만 아직 아니다.
3. **stroke pen=8 (4.124 ms, 목표 2 ms).** 현재 스팬 쓰기 + 호출 단위 중복 제거 +
   dense 인덱스 상태다. pen=64가 59배 나아진 것은 행 런이 길어 덮어쓰기를 거의 없앨 수
   있었기 때문이고, pen=8은 런이 8픽셀이라 덮어쓰기 비율이 낮아 남는 게 호출 수다.

**하지 않은 것 두 가지** (둘 다 같은 이유로 손대지 않았다 — 측정 없이는 켜지 않는다):

- **rayon을 `comp_cache/paint.rs`에 넣지 않았다.** §11-5에 적었듯 6 ms 프레임 예산
  경로이고, 더티 청크가 수십 개일 때는 스레드 풀 기동 비용이 예산을 그대로 먹는다.
- **청크당 1비트 존재 비트맵을 넣지 않았다.** §11-2-1의 "무엇을 포기했나"를 본다.

## 12. Module 2 — `perflab`: 두 후보를 **재고하지 않고** 재고한 결과 (2026-10-13)

§11에서 이미 채택한 것들 뒤에 "더 있을 것 같다"는 두 제안을 받았다.

1. **마스크 상수를 미리 저장** — `1`, `11`, `111`, `1111`, … 을 테이블로 만들어 두고
   시프트 대신 로드로 바꾸는 비트 트릭 관습.
2. **인덱스를 더 나은 구조로** — BTreeMap 대신 "그냥 배열", 또는 union-find 류.

요청대로 **엔진 코드는 한 줄도 건드리지 않고** `crates/engine/src/perflab/`와
`crates/engine/examples/perflab.rs`로만 만들었다. 이 모듈은 **엔진 어디에서도
호출되지 않으며, 통째로 지워도 엔진의 바이트는 하나도 달라지지 않는다.**

```
cargo run -p pixel-engine --release --example perflab
```

측정 규칙: median-of-9, `black_box`로 DCE 방지, 모든 인덱스는 **동일한 루프**를
`ChunkIndex` 트레이트로 돌린다(동적 디스패치 없음). 픽스처는 **두 개**를 썼다 —
**A = 2176청크가 전부 차 있는 최대 캔버스**, **B = 실제 `stroke_segment`이 그린
590청크**. B가 청크를 *획 순서*로 만든다는 점이 이 실험의 핵심이다.

### 12-1. 마스크 상수 — **기각**

| 측정 (200k회 mark_range) | median | 비고 |
|---|---:|---|
| 현행 `alpha::mark_range` (shift + 가드) | 0.280 ms | base |
| 같은 산술, 복사본 | 0.289 ms | 1.03× — 노이즈, 둘은 같은 코드 |
| **branchless, 테이블 없음** | 0.266 ms | **0.95×** |
| **64항목 폭 테이블** | 0.251 ms | **0.90×** |
| 순수 마스크 연산만 — 산술 | 0.429 ms | base |
| 순수 마스크 연산만 — 폭 테이블 | 0.423 ms | **0.98×** |
| 순수 마스크 연산만 — **64×64 테이블 (32 KB)** | 0.553 ms | **1.29× — 느림** |

**표의 10%는 "상수를 미리 계산해서" 이긴 게 아니다.** 순수 마스크 연산만 떼어 보면
테이블과 산술이 **0.98×로 사실상 같다**(0.423 vs 0.429). 테이블이 이긴 건
`width >= 64` **가드 하나**를 없앴기 때문이다 — 가드만 없앤 branchless 버전이 0.95×,
거기에 테이블을 얹으면 0.90×. 즉 절반은 분기 제거, 나머지 절반은 루프가
`mask[w] |=` 의존 체인에 묶여 있어 ALU를 하나 덜 쓰는 게 체인을 짧게 만든 효과다.

**그래도 채우지 않는다.** `mark_range`는 pen=64 스트로크에서 약 260만 번 불리고
건당 1.4 ns라 **29 ms 항목의 3.6 ms(12%)**다. 10%를 통째로 줘도 **0.36 ms, 항목의
1.2%** — 프로파일에서 안 보이는 크기다. 표는 64×64가 더 심하게(1.29×) 밀린다.

**부수 검증 — 커버리지 비트맵은 이 실험의 유일한 큰 승자였다.** 같은 질문
("이 청크에 커버리지가 있는가?")을 두 방식으로:

| | median | 비고 |
|---|---:|---|
| 커버리지 비트맵 — **16 u64** | 0.001 ms | base |
| 청크 바이트 스캔 — **512 u64** | 0.030 ms | **29.7× 느림** |

RGBA가 stride 4라 8바이트가 픽셀 2개만 덮기 때문에, 바이트를 보면 4 KB를 읽어야
한다. §11-2에서 넣은 비트�스크가 이 30배를 회수한 것이고, **이미 채택된 쪽이 옳았다.**

### 12-2. 청크 인덱스 — **현행(dense 배열) 유지**

두 픽스처의 핵심 수치 (비고: `dense array (ENGINE)` 가 1.00×):

| 접근 패턴 | A: 2176청크 전부 존재 | B: 실제 그리기의 590청크 |
|---|---|---|
| composite sweep | dense 1.00× · **arena 1.19×** · BTree 4.3× · Hash 5.0× | dense 1.00× · **arena 1.00×** · BTree 7.3× · Hash 7.7× |
| row scan (fill) | dense 1.00× · arena 1.25× · BTree 12× · Hash 20× | dense 1.00× · arena 1.00× · BTree 20× · Hash 20× |
| **pen-64 쓰기** | dense 1.00× · **arena 1.41×** · BTree 9.1× · Hash 12.9× | dense 1.00× · **arena 1.43×** · BTree 9.8× · Hash 12.7× |
| snapshot ×20 | dense 1.00× · arena 1.02× · BTree 1.04× · Hash 0.99× | dense 1.00× · **arena 0.94×** · BTree 1.04× · Hash 0.97× |
| ordered walk | dense 1.00× · arena 1.20× · BTree 3.0× · **Hash 33×** | **BTree 1.00× · arena 2.4× · dense 2.9×** · Hash 9× |

#### arena가 진 이유 — 두 겹이 아니라 **세 겹**이었다

`Vec<Option<Box<Cell>>>`는 슬롯을 읽은 **뒤 1-hop**이다. 슬롯(8바이트) 안에 이미
Box 포인터가 들어 있으므로. arena는 슬롯에서 `u32` 오프셋을 읽고 **arena[j]를 한 번
더 읽어야** 데이터에 닿는다. **의존 로드가 하나 더 많다** — 그리고 그 하나가 41%
(pen-64 쓰기 2.07 → 2.92 ms)를 온통 설명한다.

arena가 판보려던 "청크가 메모리에서 붙어 있어 locality가 좋다"는 전제 자체가
** 측정에서 거짓이었다.** 그래서 `build_in_key_order`(청크를 `chunk_key` 오름차순으로
할당)를 따로 만들어 **상한**을 측정했는데 — composite sweep에서 dense 0.007 vs
arena-KEY 0.009 ms로, **정렬된 할당조차 dense를 못 이겼다.** 청크는 4 KB이고
스윕이 읽는 건 128바이트 마스크라, 순서와 무관하게 메모리 경계가 지배한다.

#### union-find는 이 문제에 해당하지 않는다

union-find는 두 집합의 **합집합 연산을 상각**하는 구조다. 청크 저장소에는 그런 연산이
없다 — 청크는 서로 독립적으로 생성·삭제되고, "살아 있는 청크의 집합"을 물어보면
슬롯 테이블이 이미 그것이다. union-find를 넣으면 프로브마다 **슬롯 로드 2회**가
추가되는데, 지금은 1회가 답을 내고 있다. 후보로도 유효하지 않다.

#### HashMap

JS의 `Map`에 가장 가까운 구조지만 probe는 BTreeMap과 대등하고(12.9× vs 9.8× 느림),
**저장 직렬화가 결정적이지 않다** — contract §2 rule 8 때문에 매 저장마다 정렬이
필요하고, `ordered walk`에서 **9~33배** 느렸다. JS가 `Map`을 쓰면서도 결정적인
이유는 JS 트리가 `sort`를 명시적으로 하고 있기 때문이다(§2의 contract rule 8).

#### dense가 되돌아온 유일한 대가 — ordered walk

**픽스처 B에서 dense가 BTreeMap보다 2.9× 느리다.** 2176개 슬롯을 훑어 590개만
방문하기 때문이다. 절대값은 2 µs이고 직렬화는 base64+JSON이 지배하므로
**기록하고 받아들인다.** 고치려면 청크당 1비트 존재 비트맵이 필요하고 — 그건
§11-2-1에서 이미 "저장/직렬화가 병목이 될 때"로 미룬 그 항목이다. 지금은 아니다.

| 후보 | 판정 | 근거 |
|---|---|---|
| 마스크 상수 테이블 | **기각** | 마이크로 10%, 실제 항목의 1.2%. 순수 연산으로는 0.98× — 이득이 상수가 아니라 분기 제거에서 나왔고 그것은 0.95×뿐 |
| 64×64 마스크 테이블 | **기각** | 1.29× 느림 (32 KB가 L1에 안 들어감) |
| branchless `mark_range` | **보류** | 0.95×이고 공짜지만, 적용 대상 연산이 항목의 12%이고 그 5%가 0.2%. 프로파일에서 보이지 않음 |
| lane 확장(repunit) | **기각** | 엔진에 쓸 자리가 없음. 커버리지 비트맵이 이미 그 일을 128바이트로 끝내고 있다 |
| SWAR "any byte nonzero" | **기각(전제 오류)** | 정렬된 워드의 "8바이트가 전부 0인가"는 **`v != 0` 그 자체**다. 트릭이 없다. 첫 구현이 `haszero(v) != 0`으로 **이름과 반대로** 쓰여 있었고 테스트가 `probe 0`에서 잡았다 |
| arena (`u32` 오프셋) | **기각** | pen-64 쓰기에서 1.4× **느림**(의존 로드 하나 더). 정렬 할당으로 해도 못 이김 |
| union-find | **해당 없음** | 청크 저장소에 합집합 연산이 없다 |
| HashMap | **기각** | probe가 느리고, 결정적 직렬화 비용 9~33× |
| **dense 배열 (현행)** | **유지** | 5개 접근 패턴 중 4개에서 1위. ordered walk만 손해이고 그것도 2 µs |
